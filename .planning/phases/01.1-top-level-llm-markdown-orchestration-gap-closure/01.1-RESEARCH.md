# Phase 01.1: Top-level LLM Markdown Orchestration Gap Closure - Research

**Researched:** 2026-02-27
**Domain:** Persistent top-level markdown-guided skill orchestration
**Confidence:** HIGH

<research_summary>
## Summary

The existing Phase 1 foundation introduced strict runtime contracts but still
uses Python-owned orchestration flow in `RetrieveSkill`. The user requirement is
clear: orchestration policy must live in markdown-guided LLM behavior with a
persistent top-level orchestrator session that owns state and spawn decisions.

The best-risk path is:
1. Define strict markdown skill protocol (top-level + sub-skill specs).
2. Implement orchestrator session runtime and tool interface where Python is
   execution plumbing only.
3. Implement sub-skill runner + memory-search tooling with tests proving
   top-level state continuity and LLM-owned branching.
</research_summary>

<architecture_patterns>
## Recommended Patterns

### Pattern 1: Policy-in-markdown, runtime-as-plumbing
- Markdown defines decisions and allowed actions.
- Runtime enforces schema/guardrails and executes tools.

### Pattern 2: Persistent orchestrator state
- Keep one top-level state object for full lifecycle.
- Sub-skills are spawned/executed as tool actions and return structured payloads.

### Pattern 3: Explicit tool protocol
- Top-level actions: `spawn_sub_skill`, `direct_memory_search`, `return_final`.
- Sub-skill tools include memory search and optional helper actions.

### Anti-pattern to avoid
- Hardcoded `if/else` product routing logic in Python that bypasses markdown
  policy.
</architecture_patterns>

<open_questions>
## Open Questions

1. Transport-level API semantics for “single persistent call” across providers.
   Recommendation: model as one persistent top-level session abstraction where
   internal transport turns are hidden from policy logic.
2. Sub-skill concurrency for multi-spawn in one step.
   Recommendation: start sequential/controlled fan-out in Phase 01.1 and defer
   aggressive parallelism.
</open_questions>
