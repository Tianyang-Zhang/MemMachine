# Phase 3.1: Prompt-to-Markdown Parity Hardening - Research

**Researched:** 2026-02-28
**Domain:** Legacy prompt parity translation into strict markdown skill specs
**Confidence:** HIGH

<user_constraints>
## User Constraints (from CONTEXT.md)

### Locked Decisions
- Translation must preserve legacy behavior with near-literal fidelity.
- Original wording should be preserved where possible.
- Ambiguous policy language must be resolved deterministically.
- All explicit constraints/tie-breakers/bans from legacy prompts are required.
- `tool_select`, `coq`, and `split` markdown files must use a fixed section
  order and one-to-one prompt-block mapping.
- Each file must include a dedicated `## Examples` section.
- Output contracts must follow the new skill workflow contract style while
  remaining strict (`v1`, required keys/types/enums, fail-closed semantics).
- Keep legacy examples and add new workflow-aligned examples (3-5 per skill),
  including fallback/tie-breaker demonstrations.

### Deferred (Out of Scope)
- Deleting legacy Python prompt constants.
- Prompt compression/optimization after parity completion.
</user_constraints>

<research_summary>
## Summary

Current markdown specs are intentionally short and still include shorthand
translation placeholders. They do not yet encode full operational rules from:
- `TOOL_SELECT_PROMPT`
- `COMBINED_SUFFICIENCY_AND_REWRITE_PROMPT`
- `SPLIT_QUERY_PROMPT`

Phase 3.1 should be split into:
1. Policy translation hardening (rewrite all three markdown skill specs).
2. Parity guardrails (tests that fail on missing constraints/placeholders).

This separation keeps Phase 3.1 focused: first establish authoritative markdown
policy bodies, then lock them in with regression checks.
</research_summary>

<architecture_patterns>
## Recommended Patterns

### Pattern 1: Fixed Canonical Section Order
Keep one deterministic order across all sub-skill files (Intent -> Rules ->
Tools -> Output Contract -> Examples -> Failure Modes).

### Pattern 2: Contract-First Strictness
Output contract is the machine boundary: explicit required keys/types/enums and
what runtime should do on malformed/missing fields.

### Pattern 3: One-to-One Block Preservation
Each major legacy prompt block must map to a visible markdown subsection. Avoid
combining unrelated rules into summary bullets.

### Pattern 4: Example Duality
Retain representative legacy examples while adding workflow-contract examples
that show what sub-skill payloads must look like in current runtime.
</architecture_patterns>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: Partial translation disguised as parity
**Mitigation:** Add tests that assert presence of critical policy terms and
forbid placeholder phrases.

### Pitfall 2: Output contract drift from runtime expectations
**Mitigation:** Keep contract keys aligned to current skill workflow payloads
while preserving legacy decision constraints.

### Pitfall 3: Losing tie-breakers and edge-case defaults
**Mitigation:** Add explicit tie-breaker/fail-closed sections and at least one
example per critical edge case.
</common_pitfalls>
