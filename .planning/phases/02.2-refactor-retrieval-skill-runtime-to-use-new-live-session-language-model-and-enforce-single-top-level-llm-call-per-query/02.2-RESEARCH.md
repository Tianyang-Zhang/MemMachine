<user_constraints>
## User Constraints (from CONTEXT.md)

### Locked Decisions
- Python must initiate one top-level LLM runtime call per query.
- Top-level runtime call includes markdown policy + tool schemas.
- Tool execution loops stay inside the active live session chain.
- Tool functions may issue additional LLM calls (allowed).
- Top-level decision authority remains in LLM, not Python branch policy.
- Safety fallback behavior must remain intact.

### Claude's Discretion
- Instrumentation location and assertion mechanics.
- Wiring details between retrieve runtime and session runtime class.

### Deferred (OUT OF SCOPE)
- Cross-provider abstraction work.
- Performance optimization beyond correctness.
</user_constraints>

<research_summary>
## Summary

Phase 02.1 introduces the live OpenAI session runtime. Phase 02.2 should now
consume that runtime in retrieval orchestration and enforce the single-call
invariant at integration boundaries.

Key implementation principle:
- one `run_live_session(...)` entry at top-level per query,
- function callbacks execute tools and return outputs within that active chain,
- nested LLM calls are permitted only inside called tools/sub-skills.

This produces the behavior the user requested without requiring Python to run
its own explicit top-level decision loop.
</research_summary>

<architecture_patterns>
## Architecture Patterns

### Pattern 1: Top-level call gateway
Wrap top-level session start in one method and centralize all per-query
orchestration entry there.

### Pattern 2: Callback-only tool execution
Tool handlers should be pure runtime callbacks invoked by live session events,
not a second top-level orchestration loop.

### Pattern 3: Invariant-first tests
Integration tests should assert:
- one top-level session invocation per query,
- callbacks can execute multiple tools,
- finalization still returns proper fallback/trace data.

### Anti-pattern to avoid
Calling top-level `generate_response` again outside the live session adapter for
continuation logic.
</architecture_patterns>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: Hidden second top-level call
Fallback/retry paths can accidentally create a second top-level session start.

### Pitfall 2: Counter includes nested tool LLM calls
Metrics can miscount and treat nested sub-skill calls as top-level calls.

### Pitfall 3: Safety regressions during refactor
Switching transport layer can break existing fallback reason propagation.
</common_pitfalls>
