<research_summary>
## Summary

Current retrieval skill orchestration still performs Python-driven repeated
`generate_response` turns and parses tool calls each turn inside runtime code.
That conflicts with the intended communication pattern where the OpenAI
function-calling session remains active and receives tool outputs iteratively.

The implementation should introduce a dedicated OpenAI session driver that:
1. starts with markdown system prompt + tool schemas,
2. executes requested function calls,
3. sends `function_call_output` (and required reasoning items) back with
   `previous_response_id`,
4. continues until a terminal final response is produced.

Then `RetrieveSkill` and `SubSkillRunner` should be refactored to use this
session driver as orchestration transport.
</research_summary>

<external_alignment>
## External API Alignment (OpenAI)

From OpenAI official docs:
- Function-calling flow requires: model emits function calls, app executes tool,
  app sends tool result back as `function_call_output`, then model continues.
- Reasoning-mode responses can include reasoning items that must be passed back
  with function outputs for next turn.
- Conversation continuity uses response chaining with
  `previous_response_id` for stateful follow-ups.

Practical implication for this phase:
- Do not emulate with independent one-shot requests that rebuild policy state
  externally each step.
- Implement explicit chained session loop aligned to Responses API semantics.
</external_alignment>

<architecture_patterns>
## Architecture Patterns

### Pattern 1: Chained Responses session driver
- Keep `response_id` from each model response.
- Feed tool outputs back with `previous_response_id`.
- Continue until no further function calls and final text is available.

### Pattern 2: Tool registry boundary
- Runtime owns tool execution handlers and error capture.
- Session driver only maps OpenAI function-call payloads to handler invocations
  and envelopes results.

### Pattern 3: Skill-runtime integration adapter
- `RetrieveSkill` and `SubSkillRunner` call one high-level
  `run_live_session(...)` entrypoint.
- Markdown policy stays in prompt/spec; Python does protocol + guardrails.

### Anti-pattern to avoid
- Keeping orchestration in one-shot `generate_response` loops and treating each
  model call as isolated state.
</architecture_patterns>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: Losing call linkage
If `call_id` is not preserved into `function_call_output`, the model cannot
associate tool results with issued calls.

### Pitfall 2: Dropping reasoning items
For reasoning responses, omitting reasoning items between turns degrades model
continuation quality or can break expected follow-up behavior.

### Pitfall 3: Unbounded live loop
Without turn/time limits, function-calling sessions can run indefinitely.

### Pitfall 4: Partial migration
Adding new session code without switching retrieve/sub-skill entrypoints keeps
old behavior active and fails phase intent.
</common_pitfalls>
