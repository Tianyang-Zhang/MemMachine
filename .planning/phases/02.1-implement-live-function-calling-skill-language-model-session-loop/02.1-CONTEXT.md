# Phase 02.1: Live Function-Calling Skill Session Loop - Context

**Gathered:** 2026-02-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Implement a provider-specific skill language-model runtime that uses OpenAI
Responses API function calling as the execution protocol for skill orchestration.

This phase is about runtime communication semantics: one persistent top-level
LLM session that requests tool execution, receives tool outputs, and decides the
next action until final response.

Out of scope for this phase: non-OpenAI providers and accuracy optimization.

</domain>

<decisions>
## Implementation Decisions

### OpenAI API path
- Use OpenAI function-calling behavior from the official Responses API guide as
  the source protocol for this phase.
- The runtime provides tool schemas/functions and executes them when requested
  by the model.
- Other providers are deferred and must not be added in this phase.

### Persistent communication model
- The top-level skill starts from one LLM session call with top-level markdown
  policy + available tools.
- The session remains logically active while Python executes requested tools and
  returns `function_call_output` payloads back into the same response chain.
- The runtime must preserve response-chain continuity using OpenAI conversation
  state semantics (`previous_response_id` chaining).

### Tool orchestration authority
- Top-level LLM decides whether to:
  - directly call memory search,
  - spawn one or multiple sub-skills,
  - or finalize response.
- Runtime must not hardcode product routing/branch policy in Python.
- Sub-skills also follow markdown rules and can call MemMachine memory search.

### Bounded execution and reliability
- Session runtime must enforce bounded execution (turn budget + timeout + retry
  policy) to avoid unbounded loops.
- Tool execution and session limit failures must produce explicit fallback
  reason metadata.

### Code hygiene for replacement
- Remove or replace incorrect one-shot skill language model assumptions.
- Keep package exports/tests consistent after replacement (no dangling imports).

### Claude's Discretion
- Exact class/module names for the OpenAI session runtime.
- Internal event/telemetry payload schema as long as state is sufficient for
  top-level orchestration and debugging.

</decisions>

<specifics>
## Specific Ideas

- Add a dedicated language-model adapter that runs a live OpenAI function-call
  session loop and returns full tool execution transcript + final response.
- Reuse `ResponseFunctionToolCall` parsing semantics and carry reasoning items
  between turns when present.
- Refactor top-level/sub-skill runners to consume this adapter instead of
  ad-hoc repeated `generate_response` orchestration.

</specifics>

<deferred>
## Deferred Ideas

- Bedrock/Anthropic/other provider live-session adapters.
- Unified cross-provider function-calling abstraction layer.
- Parallel tool-call execution policies beyond correctness baseline.

</deferred>
